- 最终回答前综合文档、代码和结构化工具结果判断证据是否充分。
- 整改时重新核对实现，并验证聊天、RAG 问答与测试入口的行为一致性。

## 已整改：Evals 长期停留在运行中（2026-10-24）

- 原因：评测通过进程内 `BackgroundTasks` 运行，后端退出后任务消失，但数据库中的 `queued/running` 未收尾；前端持续查询旧记录，并把部分异常终态显示为“运行完成”。实际发现一条 10 月 22 日停在第 1/5 条 RAGAS 评分的遗留记录。
- 完整评测和异常指标重评分共用任务控制：默认总时限 **1800 秒（30 分钟）**，由 `EVAL_JOB_TIMEOUT_SECONDS` 配置；保留单项 Judge 的 `RAGAS_TIMEOUT_SECONDS=120`，两者独立。超时或执行异常记录为 `error`，不会伪造质量结论。
- 增加 `POST /api/evals/{eval_id}/cancel`，支持排队取消、运行中取消及重复取消。取消先持久化 `cancelled`，再通知本地任务；运行器每秒检查持久化状态，在下一进度写入前也会检查。数据库条件更新阻止迟到进度/结果把已取消任务改回运行或成功。
- 捕获任务取消并关闭数据库会话；正常退出时记录错误，强制退出遗留的活跃记录在下次启动时统一改为 `error`。前端对这类错误仅显示“评测出错，请重新运行”，不展示中断原因；主动取消显示“已取消”。
- 增加 `POST /api/evals/{eval_id}/rerun`：创建新 Eval ID，保存 `rerun_of`，保留原记录。新提交的完整评测保存实际用例、Top-K、Judge 开关和评测集版本，重跑复用这些输入；重评分重跑继续复用原问题、回答及证据，不重新调用 ChatAgent。运行中记录需先取消再重跑。
- 兼容旧自动冒烟记录：缺少完整输入时按当前资料重新生成用例，并在评测集说明中明确记录；不声称重现旧题目。其他缺少输入的旧记录要求从评测集入口重新提交。重跑使用当前仓库知识和模型配置，不提供完整环境快照回放。
- 前端增加“取消评测”和“重新运行”按钮，错误/取消后停止进度轮询并恢复提交入口；异常记录不再显示“运行完成”，空报告不再给出“可以进入回归”的误导建议。
- 验证：新增 **15 项**任务及 HTTP 接口回归，覆盖总超时、依赖吞掉取消后的迟到结果、排队/运行取消、持久化取消检测、取消与结果写入竞争、正常退出、启动收尾、历史输入复用、旧冒烟兼容和重评分重跑；后端全量 **303 项通过**，前端生产构建通过，运行保护 **7 项通过**。
- 实际运行：已重启本地后端并通过健康检查，原 `029d6d71` 记录由 `running` 改为 `error`，浏览器确认错误状态和可用的“重新运行”按钮。接口测试使用隔离数据库和可控评测函数，未额外调用真实模型。数据见 [Evals 任务控制验证](evaluations/eval-job-controls-2026-10-24.json)。

实现边界：沿用当前单 worker 的进程内任务执行方式，无新增队列、数据库表或聊天链路修改。取消和超时通过异步协作停止后续步骤，不能撤销已经发出的模型请求，也不能强行终止正在执行的同步 CPU 运算；多 worker 部署前应改为带任务归属/租约的恢复策略，避免启动收尾影响其他 worker。

## Agent 对比实验室：基础首版

记录日期：2026-10-21。

状态：待实施。以下为计划范围，实施前需核对工具边界与验收条件。

### 目标与使用流程

在独立实验界面使用同一问题、上下文和固定数据，对比基线 A 与候选 B 的回答、工具调用过程及消耗，帮助验证提示词或模型配置调整是否有效。

1. 前端从基线 A 复制创建候选 B，选择修改提示词、后端已配置的模型及该模型支持的参数。
2. 后端校验并保存候选配置，返回版本 ID；版本可重复使用，尚不改变日常聊天配置。
3. 用户选择实验用例、固定数据、A/B 版本和验收条件，手动发起对比。
4. 后端为 A、B 分别创建独立 ChatAgent 对象和执行任务，从任务起点运行并保存结果；通常不需要启动两套后端服务。
5. 前端展示运行状态、双栏工具轨迹、回答和验收结果，支持查看首次路径分歧及各步详情。

### 首版范围

- 只比较提示词、模型及受支持参数的配置版本。固定并记录 Agent 代码、工具集、Skill 版本/指令摘要和检索配置，避免其他变量混入比较。
- 实验参数通过运行实例注入，不修改全局 settings、正常聊天的模型对象或默认配置；基础首版不自动发布候选版本。
- 复用现有 Evals 页面、ChatAgent、trace 和评测基础，新增“Agent 对比实验”标签页或独立详情页；日常聊天继续单版本、单次生成，不默认双跑或展示新旧对照。
- 聊天消息菜单可增加“创建对比实验”，将问题和相关上下文带入实验。旧聊天没有完整录制数据时，只能作为新实验的题目来源，不标记为严格复现当时现场。
- 首版工具限定为只读且可隔离的工具，支持固定代码快照读取和已录制工具响应；执行路径不同导致的新请求，不能随意复用不匹配的旧响应。
- 对未录制且无法在固定环境执行的工具请求，显式标记回放缺失/实验不完整，不悄悄访问实时环境，也不将其混作可比的完整结果。
- 实验使用独立记录和隔离上下文，不污染正常聊天消息、长期记忆及正式业务记录，不执行 GitHub 写入或任意命令。
- 不纳入首版：任意历史后端代码版本并行运行、任意节点续跑、完整知识库/向量索引快照、无限制的新查询回放、自动修改生产默认版本。

### 后端实施要点

- 增加版本、实验用例、实验任务/运行及对比结果的持久化结构，区分“版本配置”“临时运行实例”和“对比实验”。
- 提供可用模型与参数能力查询、候选版本创建/读取、实验提交、运行状态和结果查询等接口。此处仅约定接口职责，具体路径实施时确定。
- 在工具结果被摘要压缩之前增加录制入口，保存脱敏后的完整输入输出、错误、耗时、工具标识及规范化参数；现有简略 trace 继续用于聊天展示。
- 固定并保存实际输入上下文、提示词内容/摘要、模型参数、代码快照标识、工具/Skill 信息和检索设置；快照不足时明确比较条件不完整。
- 在工具调用边界增加实验适配器，根据工具与规范化参数返回录制结果，或在独立只读快照上执行受支持的查询。
- 后台执行 A/B 任务，持久化 queued/running/completed/failed 等状态；首版进程重启后将遗留任务标记为中断并允许重跑，不承诺断点恢复。
- 比较最终任务验收、必要工具覆盖、重复调用和首次路径分歧；路径不同、工具更多或更少不直接等于质量更好。
- Token 区分模型实际返回值与估算值；耗时标明录制/回放模式，不将固定响应的执行耗时冒充真实线上工具性能。

### 前端展示

- 实验列表：用例、A/B 版本、创建时间、执行状态和验收摘要。
- 创建实验：问题/上下文、基线 A、可编辑候选 B、固定数据说明、验收条件和运行按钮。
- 结果详情：上方展示版本与数据条件，中间双栏展示步骤、工具和回答，下方展示验收与消耗对比。
- 步骤可展开查看参数、完整工具结果、错误与检索来源，并高亮首次路径分歧。
- 明确区分运行失败、回放数据缺失、验收未通过和正常完成；避免只给一个没有依据的“B 更好”结论。

### 验收标准

- 不改全局配置、不重启后端即可创建 B 并运行配置对比，正常聊天仍使用原默认配置。
- A/B 并发或顺序运行均不串用状态、参数、上下文、临时文件或业务写入。
- 相同固定条件下能查看完整工具轨迹与回答差异，实验条件不一致或录制缺失时明确提示。
- 可以复用保存的版本与用例再次实验，后台任务状态和已完成结果刷新后可查询。
- 验证未配置模型、无效参数、工具超时、回放缺失、任务中断和实验隔离等边界。
- 正常聊天、流式响应、历史消息、RAG 与现有评测链路回归通过；涉及模型随机性的质量结论使用多次运行，不能仅凭一次对比宣称改进。

工程量粗估：熟悉项目的单人全职开发，基础可用版约 10～15 个工作日；实际以实施前核对的工具范围、快照方案和界面细节为准。

改善主要体现在理解排除要求和同义表达、减少误选任务；代价是增加一次模型调用及规划等待。
任务数是计划统计，未执行专用 Agent，尚未实测最终诊断准确性、总执行耗时或调用成本改善。
原始数据见 [最终 Planner 对比结果](evaluations/planner-live-2026-10-22.json)。

剩余限制：一次模型输出漏加用户要求的 CI → PR 顺序；现有语义校验不能保证任意自然语言约束。
这批用例是开发验证样本，不代表线上准确率为 95%，也未证明最终诊断质量或总执行成本提升。
后续更大独立样本、顺序语义校验和规划延迟优化尚未实施；此前“Agent 对比实验室”仍为独立待办。

完整实现、整改链路与测试数据见 [Planner 整改说明](architecture/planner-llm-upgrade.md)。

## 已整改：GitHub 写操作独立验证与执行记录（2026-10-26）

目标：用户确认 Agent 草稿后，由后端执行 GitHub 操作，再独立读取实际数据验证结果，并持久化执行与验证过程。验收依据是用户批准的草稿，不让模型自行判断“操作成功”。

- [x] 四类操作加入回读验证：创建 Issue 检查返回编号对应资源的标题、正文和类型；评论检查评论 ID、所属 Issue/PR 和正文；关闭 Issue 检查编号与 `closed` 状态；添加标签检查预期标签是否全部存在，允许保留原有其他标签。
- [x] 写入响应与验证分开保存：GitHub 写接口正常返回，只代表写入请求完成；后续独立 GET 的结果才能给出 `verified`（符合预期）、`failed`（读到数据但不符）或 `unknown`（无法确认）。验证不通过不会覆盖已经保存的写入响应。
- [x] 请求前先提交数据库：通过条件更新领取待确认草稿，并在同一事务中创建唯一执行记录和开始审计；提交成功后才发出外部写请求。同一草稿的并发确认、重复确认、确认与取消竞争不会重复发送写请求。
- [x] 请求快照记录操作、目标仓库/API 地址、Issue/PR 编号及实际写入内容；预期状态单独保存。写入结果保存 GitHub 返回 JSON 或错误分类，包含操作者和时间。记录不保存 Token、Authorization 头等凭据。
- [x] 新增 `POST /api/action-drafts/{draft_id}/verify`，保留 `draft:approve` 权限要求。它只回读数据，不重发写请求；验证过程也有开始记录、完成记录与并发保护，历次结果和依据均保留。
- [x] 网络超时、5xx 或中断不能直接推断“没有写成功”，写入状态保留为 `unknown`。关闭和标签操作可根据已知目标继续读取；创建 Issue、发表评论若未收到新资源编号，则保留无法唯一定位的原因，不通过模糊内容匹配伪造成功，也不盲目重试写入。
- [x] 服务中断后保留请求和已提交的响应；单 worker 启动时将遗留写入/验证标记为待确认，保存恢复原因，不自动重发。GitHub 成功后本地保存失败的窗口不能保证完整拿到响应，但执行前的持久化记录仍可用于排查，不能宣称跨系统事务或严格 exactly-once。
- [x] 前端安全草稿页分开展示写入与验证状态，增加“仅重新验证”和可展开的请求、预期状态、响应、错误及历次验证 JSON。历史草稿不补记为已验证。`send_report` 仍只做本地记录，明确显示“未执行外部发送/不适用外部验证”。


## 已整改：聊天长时间显示“Agent 正在分析”（2026-10-26）

- 现场：同一会话连续发送两条消息后，聊天未收尾，健康接口也超时。PostgreSQL 中一条事务持有会话行锁并等待记忆模型，另一条 `UPDATE conversations` 等待该事务；进程采样显示同步 psycopg 调用堵住主线程，导致持锁请求也无法恢复并提交。
- 根因：`SessionSealer.seal()` 只 flush 原始记录，没有提交，就开始异步提取记忆；调用方之前的 `touch_conversation()` 等写入因此跨远程模型调用持锁。
- 修复：`backend/app/services/chat_memory.py` 在原始 ChatSession 建立后立即提交已完成的回答、AgentRun、草稿和会话更新，释放写锁，再做模型记忆补充。取消或记忆提取失败不能回滚已完成的回答。
- 增加 `SESSION_MEMORY_TIMEOUT_SECONDS`，默认 20 秒，在 `backend/app/core/config.py` 定义并记录于 `.env.example`；超时沿用抽取式兜底，保存 `sealed_with_warnings` 和明确的超时原因，不再无限等待记忆补充。
- 新增 `backend/app/tests/test_chat_sealing_transactions.py` 三项回归，验证模型等待期间另一连接可更新同一会话、记忆超时兜底、取消时回答和草稿仍已提交。后端全量 **341 项通过**。
- 另在隔离 PostgreSQL schema 实测：记忆模型等待前，另一连接能读到回答和原始会话并更新相同会话行，未触发 750ms 锁等待限制；测试 schema 已清理，未调用真实模型或 GitHub。
- 已解除卡住的旧聊天事务并重启后端加载修复，8000 健康接口恢复约 1ms 响应。旧挂起请求已结束，已保存的用户消息保留；未自动重发用户消息，需刷新页面后重试一次。

边界：本次限制的是回答完成后的记忆提取等待，不代表所有 Agent 调查都必须在 20 秒内完成，也未将整个项目改为异步数据库。

## 已整改：聊天生成的 GitHub 草稿动作错误、编号未绑定（2026-10-26）

- 现场：用户输入“帮我创建一个issue 负责人是Alice 标题是前端优化 正文是改善动画”，实际生成 `comment · repository` 通用模板；补充“issue编号为#1”也仅被写进正文，确认时提示缺少有效编号。
- 根因：原动作规则只覆盖少量英文表达，无法识别中文时回落为 `write_back → comment`；工具没有专用的动作、编号、标题及正文参数，而且目标选择依赖最新同步的 Issue/PR，没有使用用户明确指定的编号。
- 新增 `backend/app/services/github/draft_builder.py`：定义 `GitHubDraftToolArgs`，提供 `action/target_type/target_number/title/content/labels/assignees`，结合明确的中文/英文表达与字段解析进行校验。创建 Issue 不需要已有编号；评论、关闭、添加标签必须有明确目标，不默认选择最新记录。支持 `#1`、`Issue编号为#1`、PR 编号及同仓库 GitHub 链接；本地尚未同步目标记录时，仍保存远程编号。
- `ChatAgent` 为安全草稿工具绑定专用 schema 并提供明确的使用说明，保留实际用户原文；`chat.py` 按校验后的字段保存真实标题、正文、编号、负责人和标签，创建 Issue 固定以仓库为目标，不绑定某条已有 Issue。模型可结合对话提供结构化参数，缺少动作/必要字段、目标冲突或链接属于其他仓库时先返回澄清，不落库无效草稿。
- 创建 Issue 支持用户明确指定的 GitHub `assignees/labels`，请求快照与预期状态同步保存；客户端实际发送这些字段，回读时核验其是否存在。负责人使用 GitHub 登录名，不能直接猜测未映射的显示名；用户名及指派权限最终由 GitHub 校验。负责人回读比较忽略登录名大小写，未实际指派则验证不通过。
- 前端展示新 Issue 自动分配编号、已有 Issue/PR 目标编号、负责人和标签；旧 `comment · repository` 草稿缺少目标时禁用确认并提示取消后重新生成。未自动修改、取消或执行已有草稿；中文操作识别有确定性兜底，但不宣称覆盖所有自然语言表达。
- 新增 `backend/app/tests/test_chat_github_drafts.py` **34 项**回归，包括截图原请求、中文/英文动作、显式编号与链接、空同步数据、避免误选最新 Issue/PR、澄清分支、专用 schema、模型工具参数到实际草稿、模拟确认写入及独立回读、负责人缺失验证失败。
- 测试：后端全量 **375 项通过**；前端类型检查和生产构建通过（原有告警保留）。采用脚本模型、隔离数据库和 MockTransport，没有额外调用真实模型或向真实 GitHub 写入。已重启后端，8000 健康正常；浏览器确认两份旧错误草稿的确认按钮禁用并显示重新生成提示。
